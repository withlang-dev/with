# i128/u128 End-to-End Implementation Plan (#914)

## Authority and scope

Execution plan for making `i128`/`u128` first-class end to end. The spec
change it entails (§4.1 primitive-type list) is normative and lands only
with Eric's blessed wording; this plan cannot amend the spec. Issue of
record: #914.

## Current state — verified by running (2026-08-31)

Far more exists than the spec admits. The wide-constant pipeline is
**complete and correct**:

- Lexer/AST: out-of-i64-range literals are stored exactly —
  `Ast.set_int_literal_exact(idx, digit_idx, radix)` keeps the digit
  text; `int_literal_exact_expr` re-parses to a 128-bit `lo`/`hi`
  magnitude with overflow and sign tracking (`src/Ast.w`).
- MIR: `MirLower.lower_int_lit_node` routes non-i64-fast literals to
  `CK_INT_EXACT` consts carrying the AST node (`src/MirLower.w:2690`).
- Codegen: `exact_int_const_llvm` materializes via
  `wl_const_int_words(ty, lo, hi, 2)` for widths > 64
  (`src/CodegenTraits.w:1854`).
- Sema: both types registered as `TY_INT` width 128
  (`src/Sema.w:2415,2420`); `c_import` maps `__int128` both directions,
  align 16.

Proven working (positive) matrix:

| Area | Evidence |
|---|---|
| wide literals, dec + hex | `(2^100 literal) >> 90 == 1024`; i128 max `>> 100 == 2^27-1`; u128 max `>> 100 == 2^28-1` |
| too-big diagnostic | `2^128` as `i128` → "integer literal does not fit expected type", loud |
| arithmetic | add/mul/div/mod correct; `__divti3` resolves via libSystem's compiler-rt builtins (self-contained invariant holds) |
| full-width compute | `(1 << 100) >> 90 == 1024`; `i64max + i64max` does not falsely trap and round-trips exactly |
| checked overflow | `u128` underflow panics ("subtraction wrapped below zero") |
| casts | `i128 → i64` truncates, `i64 → i128` extends, both correct |
| ABI | `fn f(x: i128) -> i128` round-trips; struct field, `Vec[i128]`, `match` all correct |
| suffixes | `5i128` works |

## The two real defects

**D1 — formatting truncates to 64 bits.** The value is correct in the
register; the print path narrows. `f"{i128max}"` prints `-1` (the value
mod 2^64 read as i64); `f"{2^100}"` prints `0`. Root: `std.fmt` bottoms
out in `with_fmt_i32`/`with_fmt_i64` (`lib/std/fmt.w:6-7`) — there is no
128-bit renderer, and the f-string lowering's `fmt_to_str` dispatch
(`src/MirLower.w:2984`) has no width-128 arm.

Note: this defect initially masqueraded as "wide literals silently
wrap" — `let x: i128 = <i128 max>` printing `-1` looked like a lexer
wrap. The literal was perfect; only the print lied. The `>> 100`
discriminator separates them; use it in the acceptance tests so the two
layers stay independently pinned.

**D2 — negated wide literals lose the expected-type context.**
`let neg: i128 = -<any literal above i64 range>` fails with "integer
literal does not fit **default** type (`expected_ty=0`)" even though the
annotation says `i128`. The unary-minus checking path range-checks the
bare literal against the default type instead of propagating the
annotated demand (the exact-int machinery itself handles negation —
`int_literal_exact_expr` folds `NK_UNARY UOP_NEGATE` — the demand just
never arrives). Consequence: `INT128_MIN` and every negative literal of
magnitude > `i64 max` are unspellable.

## Campaign stages

1. **D2 — thread the expected type through negated literals.** Find the
   sema branch that emits "does not fit default type" for
   `NK_UNARY(NEGATE, NK_INT_LIT)` and give it the same expected-type
   propagation the bare-literal path has. Include the `INT128_MIN`
   special case (magnitude `2^127` valid only under negation — mirror
   the existing i64.min handling at `src/Ast.w:~1049`).
2. **D1 — 128-bit rendering.** `with_fmt_i128`/`with_fmt_u128` in the
   runtime (u128 divide-by-10 loop; sign handling incl. `INT128_MIN`
   without negating it in-width), `std.fmt` surface, and a width-128 arm
   in the f-string/`fmt_to_str` dispatch. Never narrow an int before
   dispatch — dispatch on the sema width.
3. **Parsing symmetry.** `parse_i128`/`parse_u128` beside the existing
   str parse family, overflow-checked against the same exact-int words.
4. **Acceptance tests.** Behavior lane: boundary literals (max, min via
   D2, u128 max), the `>> 100` layer-discriminators, signed div/mod sign
   matrix, checked-overflow at exactly `2^127-1`/`2^128-1`, format
   round-trip (`parse(fmt(x)) == x`). Interop lane: `__int128` round-trip
   through `c_import`. `--dump-abi` on an i128 signature.
5. **Fixpoint.** If the compiler's own source starts using `u128`
   (stage 3 may), run the full battery; `stage2 == stage3` must hold.
6. **Spec §4.1.** Propose the one-line primitive-list extension
   (`i8, i16, i32, i64, i128` / unsigned mirror) for Eric's blessing —
   today the types appear only in §4.1's reserved-names clause, so the
   compiler implements a type the bible doesn't claim.

## Non-goals

No software-emulation struct, no BigInt dependency, no ABI
special-casing, and no rebuild of the exact-int machinery — it exists
and is proven. `i128` is just another `TY_INT` width; treating it as
exotic is how divergence bugs get created.
